## 2026-07-31: 角度の位置づけと h の問題

### 角度は「ラベル外」だが「対応付けゲート」には使える

Azimuth 分解能 14.5° を根拠に、**角度をラベルとして使わない判断は維持**。
ただし SNR 30〜46 dB の目標では角度が単調に振れたため、カメラ検出との対応付けで
候補を絞る**粗い方位ゲート（±20° 程度）**としてなら使える。

0727（屋内・SNR 低）では角度の標準偏差が **20.8°** で使い物にならなかった。
**SNR 依存**なので、使うなら「一定 dB 以上のフレームのみ」という条件付きに限定する。

### この時点での最大のブロッカー: h と俯角が未実測

レーダーが観測するのは斜距離 `R_slant`、カメラから得られるのは地上距離 `R_ground`。
`R_slant = sqrt(R_ground² + h²)` の換算に h が必須で、h が無いとラベル（Range ビン）が作れない。

→ **この見立ては 8/17 で覆る**（下記）。

### 地面の平面性

ホモグラフィは地面が平面であることを仮定する。**車道は排水のため中央が高いことがある**。
未検証のまま持ち越し中。

## 2026-08-17: ラベル形式の決着 — ここがカメラ側の起点

### ラベル = 共通座標系での物体の座標 + クラス。すなわち点。

カメラが返すのは bbox だが、地上座標に変換できるのは**接地点（下辺中央）＝ 一点**。
座標を共通座標系で定義すると、**接地点と主要散乱点のずれは「取り除くべき誤差」ではなく
「モデルが学習する対象」になる**。ラベルの曖昧さが消え、性能の問題に置き換わる。

### ラベルは地上座標 (X,Y) で保存する

地上座標を正本にすると、**h の推定値が後で変わってもラベルを作り直さずに再計算できる**。

**重要な帰結: カメラ側の処理に h は要らない。** h が要るのは最後の学習データ組み立て（S4）だけ。
→ 7/31 で「最大のブロッカー」としていた h は、**カメラ着手のブロッカーではなくなった**。

### h 自体もカメラから求める

```
4点マーカー ─→ ホモグラフィ ─→ 地上座標 (X,Y)
                    └─────→ h・俯角
```

**本筋はカメラ経由**。内部パラメータはチェスボードで家で較正できる。
これによりレーダーから実世界の量を取る必要がなくなった。
メジャー・下げ振りによる h の実測は、カメラ経由の値との**突き合わせ用**に残す（安価なので押さえる）。

### 精度の見積もり（8/15 完了・合成データ検証）

- 画素雑音 2 px で地上誤差 **20 m: 0.06 m / 50 m: 0.20 m**。
  レーダーの距離分解能 **0.846 m** に対し 1/4 以下 → **ラベルとして十分**
- 内部パラメータ既知なら h は **15.01 ± 0.17 m**（真値 15.0 m）で復元できた
- 外挿の代償は 1.2〜1.4 倍。横の広がりは不要

### マーカーの要件

必要なのは**マーカー同士の位置関係だけ。カメラまでの距離は不要**。
地上座標系は自分で定義してよい（マーカー1を原点、1→2の向きを X 軸）。
→ 5階から地上への距離を測る必要が無いので、レーザーが届かない問題は効かない。

| # | 要件 | 理由 |
|---|---|---|
| 1 | カメラに映る | 前提 |
| 2 | 点として一意に指せる | 「角」が良い。面や太い線は中心が曖昧 |
| 3 | ターゲットが走る地面と同じ平面上 | ホモグラフィは平面を仮定。段差の上は不可 |
| 4 | 4点が一直線に並ばない | 共線だと解けない。細長い配置も精度が落ちる |
| 5 | ターゲットが来る範囲に散らばる | 囲んだ外側は精度が急落。遠距離側に1点は欲しい |
| 6 | 地上で相互距離が測れる | メジャーが届く・立ち入れる |
| 7 | 動かない | 一度測れば使い回せる |

- 4点なら相互距離は6本。位置決定に要るのは5本なので、**6本測ると1本が検算になる**
- **6〜8点あると最小二乗で誤差が平均化でき、残差から異常点を弾ける**
- 地物は動かないので、**地上での実測は初回のみ**。毎セッション必要なのは映像上で点を指す作業（数分）だけ

### 次に効く誤差: 「bbox 下辺 ≠ 接地点」の系統誤差

上の精度検証はランダムな画素雑音しか入れていない。実際には遮蔽・検出のくせで
bbox 下辺が接地点から**偏って**ずれるはずで、**こちらの方が大きい見込み**。
→ 静止した協力者を既知位置（手前・中間・遠方の3箇所）に立たせて実測するのが最短。

## 2026-09-08: クラス設計とデータ収集

### 識別対象を vehicle から cyclist / pedestrian へ変更

車両の確保が不要になり、速度エイリアシング（±4.80 m/s ＝ 17 km/h で確実に折り返す）の
問題も消える。歩行者は 0727/0728 で既に写っており、撮ろうとしなくても集まる。

### クラス識別が「速度のしきい値」に堕ちる問題

0727/0728 の実測では、歩行者が 3本すべて ±1.20 m/s、自転車が 1.45 / 2.55 / 2.64 m/s と
**バルクのドップラーだけできれいに割れている**。距離分解能 0.846 m では体格差は見えず、
ドップラーは 16 ビンしかないのでマイクロドップラーもほとんど分解できない。
このまま撮ると、モデルが学ぶのは速度のしきい値であってクラス識別ではない。

→ **対策は撮り方: 自転車を歩行速度でゆっくり走らせる本数を混ぜる。**

### `merge_cyclist()` に pedestrian クラスを追加

それまでは自転車と対応が取れなかった `person` を「誤ったラベルは無ラベルより有害」として
捨てていた（`lone_person_as_cyclist=False`）。pedestrian をクラスに立てると、
**捨てていた検出がそのまま学習データになる**。実装は既定値の変更で済む。

## 2026-09-10: 実行環境の CUDA 対応と速度実測

### GPU 機は CUDA、CPU 機は CPU のまま（2台で torch のビルドが違うのが正常）

venv はマシンごとに別なので、共通の `requirements.txt` に CUDA 版 torch を書くと
GPU の無いノートPC が巨大なホイールを引いて壊れる。GPU 機だけが追加適用する
`requirements-cuda.txt` を分けた。デスクトップの確定値は **cu130 / torch 2.14.0+cu130**
（RTX 3060 Ti sm_86、ドライバ 591.86 = CUDA 13.1 対応）。

**`--index-url` だけでは CPU 版から入れ替わらない。** CPU 版が既に入っていると pip は
`torch==2.14.0` をローカルバージョン識別子を無視して照合し、`2.14.0+cpu` を充足済みと
判断して素通りする。`+cu130` までピンして初めて差し替わる。

### 速度は `track` 全体で約 20 倍（推論のみは約 25 倍）

`0910/bench/bench_device.py` で実測。yolo11m・imgsz=1280・本番解像度 3840×2160。

| | CPU（Ryzen 7 5700X） | CUDA（RTX 3060 Ti） |
|---|---|---|
| `track`（本番と同じ経路） | 578 ms/frame | 29 ms/frame（**19.7x**） |
| 推論のみ | 573 ms | 23 ms（24.7x） |

**GPU で速くなるのは推論だけ**で、NMS 後処理と ByteTrack の対応付け（`lap` の線形割当）は
CPU に残る。したがって所要時間見積りに使うのは `track` 側。撮影 1 分（30 fps）で
**CPU 約 17 分 → GPU 約 1.5 分**。

**入力解像度は効かない**（3840×2160 と 1920×1080 で差が出ない）。どちらも imgsz=1280 に
リサイズしてから推論するため。一方 **4K JPEG のデコードは 17 ms/枚**あり、CPU 実行では
無視できるが GPU 実行では全体の約 35% を占める。次に詰めるならここ。

FP16（`--half`）は FP32 比でさらに 1.3〜1.5 倍速いが、検出結果を変えうるので本番採用は保留。

### 本番のYOLO推論はデスクトップ固定というルールにした

速度差（約20倍）と、CPU機・GPU機で検出CSVがバイト一致しない問題（畳み込み実装の違い）を
踏まえ、**本番のラベル生成は常にデスクトップ機（GPU）で行う**運用に決定。ノートPCでは
実行しない。実行機を固定することで「2台で分担する場合はどちらで生成したか記録する」
必要がそもそも無くなる。ルールは `CLAUDE.md` に明記。

### 古い torch 記述（`2.12.1+cpu`）を実測値に修正

`docs/detection.md`・`0817/README.md` 2.5 の「`torch==2.12.1` を手でピンする」は
分離前の共有 venv 前提の記述。9/10 の venv 分離でこの制約は消えたので、
`requirements.txt` に従う形へ書き換えた。

## 未決事項

- **h・俯角の試算値（18.61 m・40.10°）の検証。** メジャー・下げ振り・傾斜計による実測と
  突き合わせる。あわせて、**較正時と現地撮影時のフォーカス設定が同一だったか**を確認する
- **ArUco / ChArUco マーカーへの切替。** 印刷して硬い台紙に固定する。solvePnP を使えば、
  近傍チェスボードでのホモグラフィを遠方へ外挿する不安を避けて、手前・中間・遠方で直接
  h・俯角を求められる可能性がある。`cv2.aruco` には **`opencv-contrib-python` が必要**。
  印刷・台紙貼り・屋外実地検証（検出距離とマーカーサイズの関係）は別途時間が要る
- **接地点の系統誤差の実測**（既知位置に静止した協力者・3箇所）
- **地面の平面性**（車道は排水のため中央が高いことがある）
- **レンズ歪み補正**を本番映像で通す（S7）
- **本番のラベル生成で FP16（`--half`）を使うか。** 1.3〜1.5 倍速いが検出結果が変わりうる。
  検出が多数出る実データで座標のずれを確認してから決める
- **速度の実データ再測定。** 現状の計測は合成フレームと較正用チェスボードのみ。人・車が
  多数写る本番映像では NMS と ByteTrack の負荷が上がり、`track` の短縮率は下がる見込み
