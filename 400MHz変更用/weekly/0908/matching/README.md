# カメラ・レーダー対応付け（S3）

`meeting/2026-09-08.md` S3「カメラ検出とレーダー検出の対応付け」の骨格実装。
**実測の同期データがまだ無いため、合成データでのみ検証済み。**

## なぜ対応付けが要るか

カメラ側は個体ごとに正解（track_id・class・地上座標(X,Y)→斜距離R）を持つが、
レーダー側の後処理（`0908/postprocess`）はピーク（range, doppler）しか出さず、
どのピークがどの個体かの手がかりを持たない。

対応付けをせず「一番近い正解」を機械的に割り当てると、
- 近接した複数目標（9/8シナリオD/Eの本命）でクラスを取り違える
- カメラの幾何計算上は存在するはずでも、レーダーが物理的に検出できていない
  （遮蔽・SNR不足）場合に、誤ったラベルを押し付けてしまう

いずれも「誤ったラベルは無ラベルより有害」（S6の `lone_person_as_cyclist=False` と同じ考え方）
に反するため、対応が一意に決まらない場合は **対応なし（None）を返す**設計にしている。

## 対応付けの手順

1. レンジゲート（`RANGE_GATE_M`、暫定 1.0 m）で候補を絞る
2. 候補が複数残り、かつ **SNRが `SNR_GATE_DB`（30 dB）以上** の候補があれば、
   角度ゲート（`ANGLE_GATE_DEG`、±20°）でさらに絞る
3. それでも一意に決まらなければ対応なし

角度ゲートを条件付きにしている理由: 0727実測（屋内・低SNR）で角度の標準偏差が
20.8°まで悪化しており、低SNRでは角度そのものが信用できない
（`0727/atlas_dat_format.md` §6.5）。±20°はDBFの主ローブ幅（Azimuth分解能14.5°）に合わせた値。

## 使い方

```python
from associate import CamDetection, RadarPeak, associate_frame

cams = [CamDetection(track_id=1, cls="cyclist", range_m=15.0, angle_deg=-15.0)]
peaks = [RadarPeak(range_m=15.1, vel_ms=2.0, snr_db=25.0)]
matches = associate_frame(cams, peaks)   # list[Match]
```

## 動作確認

`python check_associate.py` — 合成データで4パターンを確認する:
①単独目標（レンジのみで一意）②同一レンジ・角度違い・高SNR（角度で分離）
③同一レンジ・角度違い・低SNR（対応なしになる）④対応するレーダー検出が無い（遮蔽）。

## 既知の限界（骨格としての割り切り）

- **貪欲法の処理順に依存する**: カメラ検出をリストの先頭から順に処理し、
  使ったピークをその場で除外する。3体以上が絡む複雑なケースでは、
  処理順によって結果が変わりうる（今回の検証では2体までしか確認していない）
- **角度の変換式が未検証**: `CamDetection.angle_deg` は地上座標(X,Y)から
  レーダー正面基準の方位角に変換する必要があるが、この変換自体（俯角・設置位置の影響）は
  実測データが無いため未実装・未検証。今は既に方位角が分かっている前提でテストしている
- **レンジゲート幅は暫定値**: `RANGE_GATE_M=1.0` は実測の誤差統計が無い状態での仮値。
  実測データが揃ったら `add_slant_range()` の誤差実測から調整する
