## 2. ヘッダ（先頭 256 byte、リトルエンディアン）

T14RE（`0715/dat_inspect.py`）と同系統だが **TX/RX 以降のオフセットが 0x10 ずれている**【実測】。
同じ `DemoKitApp` 系でもレイアウトは機種依存なので流用時は必ず検算すること。

|---|---|---|---|---|
| 0x00 | bytes | `22 10 40 30 60 50 80 70` | マジックワード（0x1022,0x3040,0x5060,0x7080） | 【実測】 |
| 0x08 | int32 | `00 00 01 01` | バージョンと【推定】 | 【推定】 |

| 0x20 | int32 | 32 | Chirps per frame（TX2本の合計） | 【文書】と一致 |
| 0x24 | int32 | 1000 | Sampling rate [ksps] | 【文書】と一致 |
| 0x28 | double | 0.1772308 | **実効帯域 [GHz]**（文書に無い値） | 【実測】`slope × n_sample / fs` と全8ファイルで厳密一致（差 0）。§4 の 177.2 MHz をヘッダ自身が持っている |

### ヘッダ解読の情報源の内訳

意味の出どころは3系統に分かれる。**オフセット（何バイト目か）は全項目とも既知の値を
走査して見つけたもので、常に【実測】**。

| 出どころ | 項目数 | 該当 |
|---|---|---|
| 操作説明書（`0721/AtlasDemoKitApp操作説明書.pdf`） | 12 | 0x0C, 0x14, 0x1C, 0x20, 0x24, 0x30, 0x34, 0x38, 0x44, 0x4C, 0x54, 0x5C |
| ベンダー MATLAB（`Cfg.Tp`） | 1 | 0x3C |
| データ自身（他項目との厳密一致） | 1 | 0x28 |
| 推定のみ | 2 | 0x00, 0x08 |
| 未同定 | 1領域 | 0x64〜0xB3 |

MATLAB の主たる貢献はヘッダではなく処理側（レンジ／速度軸の式、窓関数、仮想アレイ構成、

### 値の裏取り（オフセット推定が正しいことの主たる根拠）

ヘッダには他項目から計算できる冗長なフィールドが5つある。オフセットを1つでも読み違えて
いればこの一致は起きないため、これが位置推定の検証になる。`atlas_provenance_check.py` が
毎回検査する。全項目 相対誤差 0.00e+00【実測】。

| 項目 | 計算式 |
|---|---|
| 0x28 実効帯域 | `slope × n_sample / fs` |
| 0x44 range_res | `fs·c0/(2·kf·1024)` |
| 0x4C max_range | `255 × range_res` |
| 0x54 max_vel | `λ/(4·PRI)` |
| 0x5C vel_res | `λ/(2·N_dop·PRI)` |

## 3. データ部（offset 256 以降）

### 3.1 フレーム構造【実測】

```
1 フレーム = 32 チャープ × 4 RX × 256 サンプル = 32,768 word (int16) = 65,536 byte
軸順序     = (Frame, Chirp, Rx, Sample)   ← Sample が最も速く回る
```

検算: (3,277,056 − 256) / 65,536 = **50.0 フレーム**（割り切れる）。
50 × 200 ms = **10.0 秒**で、録画時間と整合。

軸順序が (Frame, Chirp, Rx, Sample) であること（Rx と Chirp が逆でないこと）は
Doppler の鋭さ比較で確認した。逆順で解釈すると RX 間をまたいでチャープ列を作ることになり
位相が壊れ、Doppler ピークが 1.5 倍広がる。

### 3.2 実数サンプルである根拠【実測】

1. 生の int16 列が滑らかな正弦波（周期≈22サンプル）。IQ インターリーブなら偶数/奇数で
   別々の系列になり、隣接値がこう連続しない
2. I+jQ と解釈してレンジFFTすると、スペクトルが **±12ビンで対称**になる。
   実数信号のスペクトルが対称という性質そのもの（真の複素IQなら片側に寄る）

→ 片側スペクトルのみが有効。`np.fft.rfft` を使い、レンジビン数は 256 サンプル → 128（ゼロ埋め前）。

### 3.3 チャープは TDM で TX 交互【実測】

チャープ軸 32 本は **偶数index=TX_a / 奇数index=TX_b の交互**。ブロック（前半16本=TX_a）ではない。

| 並びの仮説 | 隣接チャープの位相差の標準偏差 |
|---|---|
| 交互（`[::2]` で1TX分を抽出） | **0.008 rad** ← 完全にコヒーレント |
| ブロック（`[:16]`） | 1.830 rad ← 位相が壊れている |

物理でも裏が取れる: 同一TXの PRI = 325 µs × 2 = 650 µs から
最大速度 λ/(4·PRI) = **±4.7957 m/s**、速度分解能 λ/(2·16·PRI) = **0.59946 m/s** となり、
ヘッダ値と小数4桁まで一致（λ = c/24.06GHz = 12.469 mm）。
**Doppler FFT は必ず同一TXの16本で行う**（32本まとめてFFTすると位相が飛ぶ）。

## 4. レンジ軸: 表示刻みと真の分解能は別物【実測＋推定】

- 帯域幅 B = 0.6923 MHz/µs × 256 µs = 177.2 MHz【文書】と一致。
  **ヘッダ 0x28 が同じ値を持っている**（0.1772308 GHz）ので、この計算はヘッダ自身で裏付けられる
- **真の距離分解能** = c/2B = **0.846 m**
- ヘッダの `range_res` = 0.2115885 m = 0.846 / **4.0**（4倍ゼロ埋めの表示刻みと一致）

つまりアプリは 256 サンプルを 1024 点 FFT にゼロ埋めして表示しており、
`range_res` はビン間隔にすぎず**分離能力は 0.846 m のまま**。
文書のデフォルト値 0.1058 m/bin は 8 倍ゼロ埋め相当と【推定】される。

**sim との対応で使うべき数字は 0.846 m**（sim の真の分解能 0.38 m より粗い）。
`docs/simulation.md` の 0.38 m/bin と並べるときは、
アプリ表示の 0.21 m/bin と混同しないこと。

## 5. 実測データの物理検証

### 5.1 レンジ変化率と Doppler の独立な一致

センサ固定なので、フレーム内のチャープ平均を引くだけで静止クラッタが落ちる（MTI）。
動体ピークを追跡した結果:

| 量 | 値 |
|---|---|
| 運動区間 | t = 1.0 〜 8.8 s（40 フレーム） |
| レンジ変化率（軌跡の直線近似） | **−0.65 m/s** |
| Doppler ピーク（中央値） | **−0.60 m/s**（ビン −1。ビン幅より −0.90〜−0.30 の範囲） |

**レンジ軸から出した接近速度と、Doppler 軸から出した動径速度が独立に一致した。**
両軸のスケール（§2 の `range_res` と `vel_res`）が妥当であることの確認になる。
符号は **接近＝負**【実測】。

### 5.2 軌跡（`range_time.png`）

明るい尾根は t=0 で **約 3.5〜4 m** から始まり、t=8.5 s に 0.9 m まで単調に接近して消える。
**ユーザーの申告「約4m離れた位置から歩いてくる」と一致**。
移動距離 ≈ 3 m / 7 s ≈ 0.44 m/s（ゆっくりした歩行）で、これも Doppler ビン −1 の範囲内。

注意点:
- 早い時刻（t=1〜3 s）に **5〜6 m にもう一つ強いローブ**がある。人体の応答が数ビンに広がった
  レンジサイドローブか、屋内のマルチパス像と【推定】。追跡がここに一度乗るため、
  スクリプトはフレーム間の連続性（1フレームの移動上限 = 最大速度 × 200 ms ≈ 1 m）で拘束している
- t=8.8 s 以降は動体応答が消える（歩き終えて静止した／レーダー直下に入った）
- `rd_map.png`（t=5.0 s）では応答が Doppler −1.8〜+1 m/s に広がっている。
  胴体と四肢のマイクロドップラーと【推定】

## 6.5 ベンダー MATLAB コードによる検証（同日追記）

`0727/matlab/AN24_02,05,06,07.m` を入手。**ATLAS は Analog Devices の DemoRad（クラス名
`Adf24Tx2Rx4`）ベース**であることが判明した。移植版は `0727/atlas_matlab_port.py`。

### 裏取りできた項目（【推定】→【文書】に格上げ）

| 項目 | 私の推定値 | MATLAB の定義 | 判定 |
|---|---|---|---|
| 光速の値 | 3e8（ヘッダ値から逆算） | `c0 = 3e8` | **一致** |
| チャープ率 | 0.6923 MHz/µs | `kf=(24.24e9-24.06e9)/260e-6` | **一致** |
| 0x3C = 325.0 µs の意味 | チャープ間隔 | `Cfg.Tp = 325e-6` | **一致** |
| 実効帯域 177.2 MHz | 帯域180MHzのうち256µs分 | コメント "only 256 us are sampled from the upchirp" | **一致・理由も判明** |
| レンジ軸の刻み | rfft(n=1024) → 0.211588542 m | `vRange=[0:NFFT-1]/NFFT*fs*c0/(2*kf)` の 1024分割 | **小数9桁まで一致** |
| 窓関数 | Hanning | `Brd.hanning(...)` | **一致** |
| TX交互（TDM） | 偶数/奇数チャープで別TX | `DataTx1=Data(1:N,:)`, `DataTx2=Data(N+1:end,:)` | **一致** |

**「表示刻みと真の分解能は別物」（§4）はベンダーコードのコメントで裏付けられた。**
ベンダー自身は NFFT=2^12（0.0529 m/bin）で表示しており、分解能とは無関係な描画グリッドである
ことが明確。

### 新たに判明した項目（推定できていなかったもの）

**仮想アレイの構成（AN24_07）**: TX2×RX4 = 8ch だが、**実際に使うのは7素子**。
1素子が重複するため平均している。しかも **RX の空間順は 1,0,2,3（0始まり）で連番ではない**。

```
素子1..3 = TX_a の RX[1], RX[0], RX[2]
素子4    = (TX_b の RX[1] + TX_a の RX[3]) / 2   ← 重複素子
素子5..7 = TX_b の RX[0], RX[2], RX[3]
```

素子間隔は λ/2（角度軸 `asin(2k/N)` がそれを前提）。**これが無いと角度FFTは掛けられなかった**。
なお `Brd.BrdGetCalDat()` の複素キャリブレーション係数8個はクラス側にあり未入手（デモでも
コメントアウトされている）。`Brd.FuSca`（ADCコード→電圧）も同様に未入手。

### 食い違った項目（重要）

1. **軸順**: MATLAB の実機ストリームは `Data` が (サンプル×チャープ, チャンネル) の行列で、
   列優先なので **RX が最も遅い軸**。一方 `.dat` は **(Chirp, Rx, Sample)** で RX が中間。
   → `.dat` を書くのは DemoKitApp であり MATLAB ではないため、別レイアウトで妥当。
   再検証しても私の解釈のほうが位相が揃う（隣接チャープ位相差 std 0.008 rad vs 1.324 rad）。
   **MATLAB の `reshape` をそのまま移植すると壊れる**
2. **速度軸のキャリア**: MATLAB は中心周波数 `fc=(fStrt+fStop)/2 = 24.15 GHz` を使うが、
   `.dat` ヘッダの `max_vel=4.79570` は **`fStrt=24.06 GHz`** を使った値と一致する（差 0.4%）。
   アプリと MATLAB で流儀が違う。ヘッダとの整合を優先して移植版は `fStrt` を採用した

### 移植して分かったこと（角度）

Doppler ビンを選んでから DBF すると、歩行区間の角度は**中央値 +4.9°・標準偏差 20.8°**。
近距離（R<2.5 m、SNR良好）では +0.9〜+14° に安定するが、遠距離では ±50° まで振れる。
`range_angle_dbf.png` の主ローブ幅も ±20° 程度で、**Azimuth 分解能 14.5° という文書値と整合**。

→ **`0725/camera_radar_labeling_plan.md` §10.6 の「角度推定は評価対象外」という判断は、
実測でも裏付けられた。**

注意: どちらの TX が AN24_07 の `Tx1` かは `.dat` から判別できない。逆だと仮想アレイが反転して
**角度の符号が反転する**。今回はターゲットがほぼ正面なので影響が見えない（要検証項目）。

### 8.2 最重要: RX の並びが明記された

> 「Rawdata のフォーマットは、**Rx2, Rx1, Rx3, Rx4** の並びとなっています」

`.dat` の RX 軸は**物理アンテナの空間順ではない**。index 0 = Rx2、index 1 = Rx1。
空間順（Rx1,Rx2,Rx3,Rx4）に戻すには file index を `[1,0,2,3]` で並べ替える。

**これは §6.5 で MATLAB（AN24_07）から借りてきた並べ替えと完全に一致する。**
§6.5 では「`.dat` の軸順は MATLAB と異なる」ことを食い違いとして記録しており、
RX の並べ替えだけを流用する点に論理の飛躍が残っていた。仕様書がこの穴を埋めた。

`atlas_export.py` の `VIRT_ARRAY`（先頭が `(0,1),(0,0),(0,2)`）と
`atlas_matlab_port.py` の `VIRT_ARRAY_SIMO = [1,0,2,3]` は**いずれも正しい**。
**既存の角度推定結果（§6.5 の +4.9°、0729 自転車走行の +20°→−6°）は修正不要**。

### 8.3 解決した要検証項目: TX の識別

§6.5 末尾の「どちらの TX が AN24_07 の `Tx1` か `.dat` から判別できない。逆だと仮想アレイが
反転して角度の符号が反転する」という項目が解決した。

仕様書の図で **先頭チャープ C1 = Tx1**（奇数チャープが Tx1）。コードの
「`tx=0` = 先行チャープ側 = Tx1」という仮定と一致するため、**角度の符号は反転していない**。

ただし図の見出しは「antenna Tx1→Tx2 の順にチャープする場合」という**条件付き**の書き方なので、
**TX の順序が設定で変えられる可能性は残る**（次回の設定確認項目に追加）。

### 8.4 仕様書でも埋まらなかった項目

本資料はアンテナ配置とデータ部の並びに限定されており、以下は依然として未確定:

- **fs・サンプル数・PRI が設定で変更可能か** ← vehicle の速度エイリアシング対応の判断材料。
  H1 で最も知りたかった項目が未解決のまま
- キャリブレーション係数（`BrdGetCalDat`）・ADCコード→電圧のスケール（`FuSca`）

→ H1 の到達点は「**データ部の並びは確定、ヘッダと設定自由度は未解決**」。
残りは別資料を当たるか、§2 の手法（設定を振って `.dat` を差分比較）で埋める。
